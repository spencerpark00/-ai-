## 0. 한눈에 보는 데이터 전략

이 프로젝트는 데이터를 많이 모으는 것이 목적이 아니다. **정비 작업 한 건을 기준으로 문서·사진·로봇 실행·정비사 판단을 연결하고, 그 정보를 사람·AI·로봇의 다음 행동을 정하는 데 사용하는 것**이 목적이다.

- 공개 FAA 문서·결함 사례·이미지·음성은 RAG·비전·음성 기능을 검증하는 데 사용한다.
- 외부에서 구할 수 없는 대한항공 작업지시·작업 단계·Work Card는 공개 정비 표준에 맞춰 합성한다.
- PoC에서 발생한 사진·작업시간·로봇 상태·정비사 승인 이력은 직접 수집한다.
- 정비사가 승인한 결과만 다음 작업에서 재사용할 수 있는 지식으로 축적한다.

> **핵심 문장**
> 공개 데이터로 AI 기능을 검증하고, 표준 기반 합성 데이터로 작업 흐름을 구현하며, PoC에서 승인된 실행 결과를 대한항공만의 정비 지식으로 축적한다.

## 2. 데이터가 흐르는 5단계

### 2.1 원천 데이터 수집

먼저 서로 흩어진 정비 정보를 수집한다.

- FAA 정비 핸드북과 정비 절차
- MMEL·AD 등 정비 판단 기준
- FAA SDR 결함·조치 사례
- 항공기 외피 결함 이미지
- 소음 환경 음성 데이터
- 모의 작업지시와 Work Card
- PoC 작업사진·음성메모·실행 로그

이 단계의 데이터는 아직 문서, 이미지, 음성, 로그 형태로 따로 존재한다.

### 2.2 같은 작업번호로 연결

서로 다른 데이터를 같은 정비 작업에 속한 정보로 묶는다. 기술적으로는 정규화·맥락화 단계에 해당한다.

#### 분리·계층 결정 3건

**① 결함후보(DefectCandidate) ≠ 결함(Defect)**

불변 원칙 **"최종 결함 판정은 정비사가 수행한다"** 를 스키마로 강제하는 장치다.

```
AI·로봇   →  결함후보만 생성 가능      (결함은 생성 불가)
정비사    →  결함후보에 판정 부여
판정(이상) →  비로소 결함으로 확정
```

한 클래스로 두면 AI 출력이 그대로 결함이 되어, 원칙이 스키마에서 사라진다.

**② 필수증빙항목(EvidenceRequirement) ≠ 증빙실물(EvidenceItem)**

전자는 "무엇을 찍어야 하는가"(작업 단계가 요구하는 항목), 후자는 실제 촬영된 사진·영상·음성이다.
분리해야 KPI **'검사·기록 증빙 자동 연결률'** 이 *요구항목 대비 실물 연결 비율*로 측정된다.

**③ 사례(Case) 계층** ★ — D-002

```
사례(Case)  [추상]                    ← `유사사례` 관계는 이 상위를 가리킨다
├── 외부사례(ExternalCase)   Phase 1   FAA SDR · ARAIB. 실행 맥락 없음
└── 검증사례(VerifiedCase)   Phase 2   PoC 환류. 정비사 승인을 거친 것만
        └─[근거]→ 작업지시              실행 맥락(단계·증빙·판정) 전체에 연결
```

상위 공통 속성만으로 CQ **A6**(외부 사례)와 **G5**(사내 검증 사례)가 **한 질의**로 답해진다.
①과 같은 패턴이다 — "외부·AI가 만든 것" vs "승인을 거쳐 확정된 것"을 **타입으로** 가른다.
§2.5의 "승인된 결과만 지식 베이스에 등록"이 **클래스 멤버십으로 강제**된다.

> 후속 KPI **'공식 출처 연결률'** 이 경고문 단위로 측정된다.

> ※ **결함 유형은 `PartCondition`에서 온다** (v3.5 신규).
> SDR의 `Nature of Condition` 코드는 **결함 유형이 아니라 운항 영향** 분류다
> (FLAME · SMOKE · VIBRATION · WARNING INDICATION · ENGINE FLAMEOUT …).
> 구조 정비(부식·균열)에는 해당 코드가 없어 **74%가 OTHER**로 몰린다 — 데이터 품질 문제가 아니라
> 코드 체계의 목적이 다른 것이다. 마찬가지로 `Precautionary Procedure`(K=NONE 79%)는
> **비상 대응**이지 정비 조치가 아니다. 둘은 결함의 **부가 속성**으로 사용한다.
>
> 실제 결함 유형은 `PartCondition`에 있다 — 채움률 100%, 정형 어휘 255종.
> **구조(53xx)에서는 81종이며 상위 2종이 77.6%를 차지한다: CORRODED(47.7%) · CRACKED(29.9%).**
> 이는 부록 3의 비전 데이터셋 탐지 대상과 일치하므로, **온톨로지의 결함 유형과 비전 모델의
> 탐지 클래스가 같은 어휘를 공유한다.**
>
> **활용** — 운항영향 이력이 있으므로, D-003의 위험등급을 팀의 임의 판단이 아니라
> **실제 운항 영향 통계를 근거로** 부여할 수 있다.

> ※ **검사위치 좌표계는 공개 실데이터에 존재한다** (v3.5 신규).
> SDR에 동체 스테이션·스트링거·버트라인·워터라인 필드가 있다. 구조(53xx) 사례 기준 채움률은
> `FuselageStationFrom` **42.1%**, `CorrosionLevel` **28.2%**, `StringerFrom` **15.1%**.
> 실제 표기 예: `BS 440+7 - 440+13.7, S20R-2 - S20R+2.4`
> → 검사 위치를 "랜딩기어 후방" 같은 임의 명명이 아니라 **업계 표준 좌표계**로 특정한다.
> 인스턴스는 여전히 Phase 2(PoC 촬영)이나, **좌표 체계 자체는 공개 데이터 근거를 갖는다.**

> ※ **공구는 종류로 모델링한다** (D-004).
> 반출·반납 상태는 개체("정비고 3번 렌치")의 런타임 상태이므로 공구 클래스의 속성이 아니다.
> 공구 클래스에 두면 같은 종류의 공구가 전부 동시에 반출된 것이 된다.
> **CQ D1**("공구 다 돌아왔나?")은 Phase 2 — 공구개체 + 실행이벤트로 답한다.

### 2.3.1 온톨로지 구축 범위

온톨로지는 한 번에 완성하지 않고 **인스턴스를 채울 수 있는 시점**을 기준으로 두 단계로 나눈다.
Phase 경계는 임의 구분이 아니라 §1 데이터 등급 경계와 일치한다.

| | 대상 | 인스턴스 소스 | 시점 |
| --- | --- | --- | --- |
| **Phase 1** | 정적 정비지식 12종 (추상 1종 포함) | FAA 핸드북 · JASC · SDR · AD (✅ 공개 실데이터) | **지금 가능** |
| **Phase 2** | 실행·판단 12종 | 합성 작업지시(🔧) · PoC 실행 로그(🎤) · 로봇 스펙 | **PoC 설계 시** |

Phase 2 객체는 지금 만들어도 채울 데이터가 없다. 다만 **PoC 이후가 아니라 PoC 설계 시점**에
정의돼 있어야 한다. 실행이벤트·정비사판정 구조가 먼저 있어야 그 형태로 로그가 남고,
그래야 §4의 KPI가 재가공 없이 산출된다.

**CQ는 30개 전체를 지금 확정한다.** 클래스 구축을 미루는 것과 요구사항을 지우는 것은 다르다.
Phase 1 스키마가 Phase 2를 막지 않는지 검증하는 기준이 CQ 30개다.

**미결 항목 — 전부 해소됨** (v3.4)

| 항목 | 결정 | 결정 번호 |
| --- | --- | --- |
| 사례를 독립 클래스로 둘지 | 상위 추상 + 외부사례/검증사례 2하위 | D-002 |
| 위험도를 클래스로 둘지 | 안전주의사항(클래스) + 위험등급(속성)으로 분리 | D-003 |
| 공구를 종류/개체로 분리할지 | Phase 1은 종류만, 개체·반출이력은 Phase 2 | D-004 |

### 2.4 오케스트레이션 실행

관계형 지식과 현재 작업 상태를 바탕으로 다음 행동을 결정한다.

| 실행 데이터 | 역할 |
| --- | --- |
| Work Order | 작업 대상, 목적, 우선순위, 현재 상태 |
| Task Step | 작업 순서, 선행조건, 수행 주체, 완료조건 |
| Skill Request | 로봇에 요청할 행동과 실행 조건 |
| Execution Event | 시작·완료·실패·재시도·타임아웃 기록 |
| Human Decision | 정비사의 승인·반려·재촬영·수동 전환 |
| Evidence | 작업 단계와 연결된 사진·영상·음성 |
| Work Record | 작업시간, 공구, 판정, 조치, 증빙을 묶은 기록 |

오케스트레이터는 다음을 관리한다.

1. 현재 단계에 필요한 절차와 정보
2. 정비사·AI·로봇 중 누가 수행할지
3. 로봇에 어떤 작업을 요청할지
4. 어느 시점에 정비사 승인을 받을지
5. 실패·타임아웃·반려 시 어디로 돌아갈지
6. 완료 후 어떤 증빙과 기록을 남길지

> ※ 위 실행 데이터는 §2.3 Phase 2 객체와 1:1 대응한다.
> Work Order→작업지시, Task Step→작업단계, Skill Request→로봇스킬,
> Execution Event→실행이벤트, Human Decision→정비사판정, Evidence→증빙실물, Work Record→작업기록

### 2.5 정비사 승인 후 지식 환류

AI와 로봇이 만든 결과를 곧바로 정답으로 저장하지 않는다.

```
로봇 촬영·AI 분석
→ Work Card 초안 생성
→ 정비사 검토
→ 승인·수정·반려
→ 승인된 결과만 지식 베이스에 등록  ← 이 시점에 검증사례(VerifiedCase)가 생성된다
→ 이후 유사 작업과 작업 배정에 재사용
```

이를 통해 작업 로그가 단순 기록에 머물지 않고, **현장 검증을 거친 정비 사례**로 전환된다.
승인되지 않은 결과는 검증사례가 될 수 없다 — 클래스 멤버십 자체가 승인 게이트다.

## 3. '대한항공만의 지식'이란 무엇인가

단순한 지식은 "어느 부품에서 어떤 결함이 발견됐다"는 사실만 담는다. 이 프로젝트는 여기에 **작업 맥락과 실제 판단 결과**를 더한다.

| 지식 유형 | 담는 내용 |
| --- | --- |
| 현상 지식 | 어느 항공기·부품에서 무엇이 관찰됐는가 |
| 실행 맥락 | 어떤 작업 단계에서 어떤 로봇 스킬과 근거 문서를 사용했는가 |
| 시간 흐름 | 이전에 어떤 검사·정비가 있었고 이후 어떤 조치로 이어졌는가 |
| 의사결정 | 어떤 조건에서 재촬영·추가 검사·수동 전환이 선택됐는가 |

> **정의**
> 대한항공만의 지식은 "어디에 어떤 결함이 있었다"는 기록이 아니라, **어떤 작업 상황에서 무엇을 참고했고, 누가 어떤 판단을 내려 실제로 어떤 조치가 유효했는지를 연결한 지식**이다.

구조적으로 이 정의는 **외부사례와 검증사례의 차이**로 나타난다. 외부사례(SDR)에는 실행 맥락이 없고,
검증사례에는 작업지시를 통해 단계·증빙·판정·승인자가 모두 연결된다.

본 PoC는 인과관계를 통계적으로 증명한다고 주장하지 않는다. 과거 사건과 현재 결함 사이의 **관련 가능성을 제시**하고, 최종 원인 판단과 결함 판정은 정비사가 수행한다.

### KPI 측정 데이터

PoC의 As-Is와 To-Be를 동일한 조건으로 비교하기 위해 다음 이벤트를 기록한다.

- 정보 검색 시작·종료 시각과 최초 검색 성공 여부
- 검사 시작·종료 시각
- 촬영 및 재촬영 횟수
- 로봇 명령의 성공·실패·타임아웃

- Work Card 작성·수정 시간
- 전체 작업 완료시간

외부 문헌 수치는 문제 규모와 목표를 정하는 참고자료로만 사용한다. 최종 효과는 PoC에서 직접 측정한 결과로 판단한다.

> ※ 위 항목은 **온톨로지에 별도 클래스로 넣지 않는다.** 실행이벤트·정비사판정에 타임스탬프가 붙으면
> 질의로 파생된다. 특히 `trial_id`·`condition`은 실험 조건이지 정비 도메인 개념이 아니므로
> 온톨로지가 아니라 **실행 로그 스키마**에 둔다.

## 5. 대표 시나리오

### 정비 작업 실행 오케스트레이션 — 사각지대 외관검사

이 시나리오의 주인공은 로봇이 아니라 **오케스트레이터**다. 로봇은 오케스트레이터가 배정한 검사 작업을 수행하고, 최종 판단은 정비사가 맡는다.

```
① 정비 작업지시 입력
→ ② 관련 절차·주의사항·유사 사례 검색
→ ③ 작업 단계를 나누고 정비사·AI·로봇에 역할 배정
→ ④ 로봇 상태 확인 후 촬영 작업 요청
→ ⑤ 로봇이 검사 위치 이동 또는 카메라 자세 조정 후 조명·촬영
→ ⑥ 엣지에서 촬영 품질 확인, 미달 시 자동 재촬영
→ ⑦ 정비사가 결과와 근거를 보고 정상·이상·재검사 필요 중 하나로 판단
→ ⑧ 판단 결과에 따라 다음 작업 배정
→ ⑨ 사진·작업시간·로봇 로그·판정을 Work Card에 자동 연결
→ ⑩ 정비사 승인 후 검증 사례로 지식 베이스에 등록
```

### 반드시 보여줄 예외 처리

| 상황 | 처리 |
| --- | --- |
| 촬영 품질 미달 | 카메라 자세·조명을 조정해 재촬영 |
| 정비사 반려 | 재촬영 또는 재검토 단계로 되돌림 |
| 로봇 오류·타임아웃 | 안전 정지 후 수동 작업으로 전환 |

각 데이터는 `work_order_id`와 `task_step_id`로 연결한다. 이를 통해 작업 요청부터 로봇 실행, 정비사 판단, 기록 승인까지 전체 흐름을 추적한다.

> **최종 정의**
> 본 프로젝트는 사각지대 외관검사를 대표 사례로, 정비 지식과 현재 작업 상태를 바탕으로 정비사·AI·로봇의 역할을 배정하고, 실행 과정의 예외를 통제하며, 승인된 결과를 다음 작업에 재사용하는 **항공정비 실행 오케스트레이션**을 구현한다.

## 6. 검증 범위

### 6.1 공개 실데이터로 검증

- 정비 문서와 유사 사례 검색 품질
- 소음 환경 음성 명령 인식
- 항공기 외피 이상 후보 탐지
- 촬영 이미지 품질 판정

### 6.2 합성 데이터와 실행 로그로 검증

> ※ 아래 항목은 검증 대상인 동시에 **온톨로지 제약(규칙)의 원문**이다.
> 온톨로지 6단계(제약 정의)에서 새로 만들지 않고 여기서 형식화한다.

| 검증 항목 | 대응 제약 |
| --- | --- |
| 작업 단계가 정해진 순서대로 실행되는지 | `precedes` 위반 금지 |
| 정비사 승인 전 위험한 다음 작업이 차단되는지 | `작업단계.위험등급 == '상' AND 작업단계.승인필요여부 == Y` 인 단계는 정비사판정 없이 전이 불가 ※ |
| 품질 미달 시 재촬영되는지 | 증빙실물 품질점수 미달 → 재촬영 실행이벤트 필수 |
| 로봇 실패·타임아웃 시 안전하게 중지되는지 | 실행이벤트 실패 → 수동 전환 외 전이 금지 |
| 정비사 반려 시 올바른 단계로 돌아가는지 | 반려 판정 → 지정 복귀 단계로만 전이 |
| 사진과 작업기록이 자동으로 연결되는지 | 필수증빙항목 전건에 증빙실물 연결 필수 |
| 승인되지 않은 결과가 지식으로 등록되지 않는지 ★ | 정비사판정(승인) 없이 검증사례 생성 불가 |
| 반출 공구가 전부 반납됐는지 ★ | 작업지시 종료 시 공구개체 현재상태 == 반납 |

### 6.3 실제 대한항공 데이터로 전환하는 방법

본 PoC의 공개 문서와 합성 Work Card는 실제 대한항공 데이터를 대신하지 않는다. 실도입 시에는 같은 데이터 구조와 연결 방식을 유지한 채 다음 데이터로 교체한다.

- 대한항공 AMM·TSM·SB
- ERP·M&E 작업지시
- 과거 정비이력과 실제 Work Card
- 정비사·조직 권한
- 실제 로봇·센서·설비 데이터

따라서 PoC의 핵심 검증 대상은 데이터 규모가 아니라, **작업지시 → 지식 검색 → 로봇 실행 → 정비사 승인 → 기록 생성 → 지식 환류가 하나의 흐름으로 작동하는지**다.


### 슬라이드 12. 오케스트레이션 데이터 구조

**헤드라인**
작업번호를 중심으로 문서·로봇 실행·사진·정비사 판단을 연결해 다음 행동을 결정한다.

**핵심 도식**
```
정비 문서·결함 사례·사진·음성
→ 같은 작업번호로 연결
→ 부품–결함–절차–로봇 행동 관계 구성
→ 수행 주체 배정·상태 변화·예외 처리
→ 로봇 실행·정비사 승인·Work Card
```

### 슬라이드 13. 대한항공만의 지식 환류

**헤드라인**
작업 결과와 정비사 판단을 축적해 다음 작업에서 다시 쓰는 검증 지식으로 전환한다.

**As-Is**
- 문서·사진·정비기록이 서로 분리돼 있다.
- 부품·결함 정보는 남지만, 작업 과정과 판단 근거는 연결되지 않는다.
- 과거 작업 결과가 다음 작업 배정과 판단에 체계적으로 활용되지 않는다.

**To-Be**
- 작업지시·절차·로봇 행동·증빙·정비사 판단을 한 흐름으로 연결한다.
- 같은 부품에서 반복된 현상과 이전 정비 이력을 함께 제시한다.
- 정비사가 승인한 조치 결과를 다음 유사 작업과 오케스트레이션에 재사용한다.

**핵심 메시지**
AI와 로봇의 결과를 그대로 정답으로 저장하지 않는다. 정비사가 검토하고 승인한 정보만 대한항공의 검증 지식으로 축적한다.
