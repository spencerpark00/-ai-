## 0. 한 줄 흐름 (블레이드 버전)

> 엔진 오버홀 중 분해된 HPC 블레이드가 검사 스탠드에 거치된다 → 정비사가 앱에서 오늘의 블레이드 검사 작업을 받는다 → 로봇 또는 직접 촬영 → AI가 이상 **후보**를 표시 → **정비사가 판정**(HITL) → 기록이 관리자 대시보드에 실시간 반영 → 승인건은 지식그래프에 환류.

기존 흐름과 **구조가 100% 동일**하다. 달라지는 것은 "무엇을, 왜 찍는가"뿐.

## 1. 로봇 필요성 논리 교체 — D-008의 핵심 서사

## 4. 데이터 흐름 — 시드→판정→집계→환류→사례 (구조 무변경)

```
seedWorks() [431행, 블레이드로 교체]
  → GET /api/works (정비사 앱 목록)
  → POST /api/works/progress (가동보드 라이브 — 무변경)
  → POST /api/works/complete → completeWork() [579행, 무변경]
      → WORKS·ACTIVITY 갱신 → GET /api/dashboard (관리자 실시간 — 무변경)
      → 승인건 Q_VERIFY_WRITE → Neo4j VerifiedCase (part=BLADE로 자동 축적 — 코드 무변경)
  → GET /api/cases (지식 탭: VerifiedCase + ExternalCase[SDR blade 118행] + 사진 자동 배정)
```

- `completeWork`·`buildDashboard`·`livePairs`·`autoTick`(데모 자동재생)·`resetWorks` — **전부 part 무관 로직. 무수정.**
- 환류는 `w.part`를 그대로 쓰므로 시드만 바꾸면 `VerifiedCase→ON_PART→BLADE`로 자동 축적된다.
- ExternalCase: SDR-2026.csv에서 필터 재적재 (T3). **실측 정정** — 핸드오프 문서의 "blade 118행"은 CSV 전체에서 'blade' 문자열이 언급된 행 수이고, 실제 사용 가능한 사례는 아래와 같다:

| 측정 | 값 |
| --- | --- |
| CSV에서 'blade' 언급 | 118행 |
| 엔진 문맥(JASC 72xx 또는 EngineModel 보유) 블레이드·베인 | 63행 |
| 그중 우리 온톨로지 결함 코드로 매핑 가능 | **32건** (BLADE 30 · VANE 2) |
| 실제 조건 분포 | DAMAGED 30 · CRACKED 1 · CORRODED 1 (원자료: DAMAGED 22 · VIBRATION 8 · BIRD INGESTION 5 · FAULTED 3 · STALLED 3 …) |

  **함의:** SDR의 엔진 블레이드 보고는 **운항 중 FOD·버드스트라이크 계열**이 지배적이며, 우리 시나리오인 **오버홀 샵의 외관 결함(부식·균열·찍힘·마모)** 분포와 다르다. 따라서 "부식 41건/균열 33건" 같은 분포를 시드에 박으면 지어낸 수치가 된다. → 결함 **분류**(어떤 결함이 생길 수 있는가)는 교범 기반으로 Cypher 시드에 두고, 결함 **통계**(몇 건 보고됐는가)는 `load_sdr_blade.js`가 실적재에서 역산해 `caseCount`·`OCCURS_ON.weight`에 SET 한다.
- 사진: `scanDefectImages()`(621행)가 `assets/defects/{key}-{n}.png` 규칙으로 자동 배정 — **기존 key(corrosion/crack/dent) 유지, 파일만 블레이드 사진으로 교체.** 서버 무수정.

## 5. 표기 체계 확정 (시드 설계)

### 5.1 결함 코드 — 기존 코드 전량 재사용, 신규 도입 없음
블레이드 결함 어휘가 기존 맵에 이미 다 있다. **NICK은 도입하지 않는다** — index.html의 `KOR`/`DEFC`/`RISK` 맵(215~222·396행), server.js `KORD`, 위험도 문안까지 연쇄 수정이 필요해지는데, '찍힘'=DENTED가 blade nick/dent를 의미상 커버하기 때문. (핸드오프 T3 스켈레톤의 NICK은 채택하지 않음 — 자산 보존 우선)

| 시드 한글 | 코드 (기존) | 블레이드 의미 |
| --- | --- | --- |
| 부식 | CORRODED | 표면 부식·피팅 |
| 균열 | CRACKED | 리딩엣지·루트 균열 (긴급) |
| 찍힘 | DENTED | FOD nick/dent |
| 마모 | WORN | 팁 마모 (tip rub) |
| 이상없음 | — | 정상 baseline |

### 5.2 작업 시드 8건 (server.js 433~438행 교체안)
건수 8 유지 (완료건 다양성 로직 446~447행이 의존). BLADE 6 + VANE 2로 구성해 판단⓪ "부품이 바뀌면 절차가 바뀐다" 서사 지원:

['BLADE','이상없음','정상',90],['BLADE','마모','주의',145],

### 5.3 위치 코드 — 엔진명은 ac 필드로, area는 스테이지·블레이드 ID
핸드오프 예시(`'CFM56-7B · HPC Stage 4 · BLD-017'`)를 그대로 area 배열에 넣으면 **ac 배열(기체)과 인덱스가 독립이라 "B777 + CFM56-7B" 같은 기종·엔진 불일치가 발생**한다 (발표 리스크). 확정안:

- `acs` 배열(437행): 기체 → **엔진 모델**로 교체: `['CFM56-7B','V2500-A5','GE90-115B','CF34-10E','LEAP-1B']`
- `frs` 배열(438행): `'HPC Stg3 · BLD-012'`, `'HPC Stg4 · BLD-017'`, `'HPC Stg4 · BLD-042'`, `'HPC Stg5 · BLD-008'`, … 10개
- index.html의 "기체" 라벨 2곳(269·300행) → **"엔진"** — 오버홀 컨텍스트에서 더 자연스럽고, 이 한 단어가 기종·엔진 매칭 문제를 구조적으로 제거

### 5.4 기타 확정값
- WO ID: `'WO-2026-0805-01'` (846행 + T3 Neo4j 시드 일치)
- 별칭 추가(75행): `'블레이드':'BLADE','blade':'BLADE','에어포일':'BLADE','베인':'VANE','vane':'VANE'` — **기존 SKIN 계열 별칭 전량 유지** (Neo4j 기존 데이터 회귀 호환)
