# MRO Copilot은 어떻게 만들어졌나 — 서비스 제작 여정

> 이 문서는 **비전공 팀원도 읽고 이해할 수 있게** 쓴 제작 기록입니다.
> 어려운 용어는 풀어 쓰고, "무엇을 왜 어떻게 했는지"를 순서대로 이야기합니다.
> 실제 서비스: **https://mro-copilot.onrender.com**

---

## 0. 한 문장으로

정비 지식을 **컴퓨터가 따라갈 수 있는 형태(지식그래프)로 정리**하고,
그 위에 **정비사가 실제로 쓰는 화면 3개**를 얹은 뒤,
누구나 링크로 열 수 있게 **인터넷(클라우드)에 올린** 것.

---

## 1. 우리가 풀려는 문제

정비 현장에는 정보가 여기저기 흩어져 있습니다. 매뉴얼 따로, 과거 사례 따로, 선배 머릿속 따로.
정비사가 "이 부품 이거 어떻게 하지?" 물어보면, 그걸 한 번에 답해주는 게 없습니다.

그래서 우리는 **흩어진 정비 지식을 하나로 연결**하고, 정비사가 물어보면 답해주는 서비스를 만들기로 했습니다.
단, AI가 멋대로 판정하는 게 아니라 **최종 판단은 항상 정비사**가 하도록 (이게 우리 프로젝트의 원칙입니다).

---

## 2. 만드는 순서 (큰 그림)

```
① 지식 정리       →   ② 지식그래프 만들기   →   ③ 화면 만들기    →   ④ 인터넷에 올리기
(무엇을 연결?)         (컴퓨터가 읽게)          (사람이 보게)         (누구나 쓰게)
```

이 네 단계를 하나씩 풀어서 설명합니다.

---

## 3. ① 지식 정리 — "무엇을 어떻게 연결할까"

### 온톨로지가 뭔가요?

**"온톨로지"** 라는 말이 어렵게 들리는데, 쉽게 말하면 **"정비 지식을 단어가 아니라 관계로 적어둔 것"** 입니다.

- 보통 매뉴얼: "유압펌프는 유압계통에 속한다" (사람이 읽는 문장)
- 온톨로지: `[유압펌프] → 속한다 → [유압계통]` (컴퓨터가 따라갈 수 있는 연결)

이런 연결을 수천 개 쌓아두면, 컴퓨터가 "이 부품이 어디 속하고, 어떤 결함이 있었고, 어떻게 고쳤는지"를
**따라가며 답할 수 있게** 됩니다.

### 왜 그냥 검색이 아니라 이걸 하나요?

정비사 질문은 두 종류입니다.
- **"이거 절차가 뭐야?"** → 매뉴얼 검색으로 답할 수 있음
- **"다음에 뭐 해야 돼? / 얘 원래 이래?"** → 매뉴얼에 안 적혀 있음. **연결을 따라가야 답이 나옴**

두 번째 종류가 우리 서비스의 핵심이라, 검색이 아니라 지식그래프가 필요했습니다.

### 무슨 데이터를 썼나요? (전부 공개된 진짜 데이터)

지어낸 데이터가 아니라 **실제 항공 데이터**를 썼다는 게 중요합니다.

| 데이터 | 무엇 | 규모 |
| --- | --- | --- |
| **FAA JASC 코드표** | 미국 항공청이 만든 항공기 계통 분류 (부품이 어디 속하는지) | 547개 코드 |
| **FAA SDR** | 실제 정비 결함 보고서 (전 세계 항공사가 올린 것) | 31,582건 |
| **FAA 정비 핸드북** | 검사 절차·공구·주의사항 | 공식 교재 |

> 핵심: 이 분류를 **우리가 지어낸 게 아니라 FAA 표준을 그대로 가져왔다**는 점.
> 심사에서 "그거 임의로 만든 거 아니냐"는 질문에 "표준입니다"로 답할 수 있습니다.

### 실제로 뭘 연결했나 (예시)

```
53 동체       →  5330 외판(SKIN)  →  SKIN 부품  →  부식 199건 / 균열 128건 ...
                                                       ↓
                                              과거 실제 사례 (좌표·원문)
                                                       ↓
                                              검사 절차 · 공구 · 주의사항
```

이렇게 계통 → 부품 → 결함 → 사례 → 절차가 **한 줄로 연결**됩니다.
정비사가 "동체 외판 부식"이라고 물으면, 이 연결을 따라가며 전부 답해줍니다.

## 4. ② 지식그래프 만들기 — "컴퓨터가 읽게" (Neo4j)

### Neo4j가 뭔가요?

**Neo4j** 는 위에서 정리한 "연결(그래프)"을 저장하는 특별한 데이터베이스입니다.
보통 데이터베이스는 표(엑셀처럼)로 저장하는데, Neo4j는 **동그라미(개체)와 선(관계)** 으로 저장합니다.
그래서 "이거랑 이거가 어떻게 연결됐나"를 따라가기에 딱 맞습니다.

### 어떻게 채웠나

1. 위의 공개 데이터(JASC·SDR·핸드북)를 컴퓨터가 읽을 수 있게 **가공**했습니다.
2. Neo4j에 하나씩 **적재**(넣기)했습니다.
3. 결과: **동그라미(개체) 약 1,300개 + 선(관계) 약 2,500개**

넣은 것들:
- 계통 598개 (항공기 부위 분류)
- 부품 141개 (외판·스트링거·프레임 등)
- 결함 81개 (부식·균열·손상 등)
- 실제 사례 500건 (SDR에서)
- 정비 절차·공구·주의사항 (핸드북에서)

### 확인도 했습니다

넣기만 하고 끝이 아니라, **제대로 연결됐는지 검사**했습니다.
예: "모든 부품이 계통에 연결됐나?" → 안 된 게 하나도 없으면 통과.
이런 검사를 통과해야 "지식그래프가 제대로 섰다"고 말할 수 있습니다.

---

## 5. ③ 화면 만들기 — "사람이 보게" (서비스 3개)

지식그래프는 개발자가 보는 내부 구조(동그라미·선)일 뿐, 정비사가 그걸 보진 않습니다.
그래서 **정비사가 실제로 쓰는 화면 3개**를 만들었습니다. 이게 우리 프로젝트의 3대 서비스입니다.

### 서비스 ① 정비사 지원 단말 — "물어보면 답해주는 화면"

정비사가 검색창에 **"동체 외판 부식"** 이라고 치면 (또는 마이크로 말하면):
- **반복 결함**: 이 부품에 어떤 결함이 몇 번 있었나 (막대그래프)
- **과거 사례**: 실제 보고서 원문 + 위치 좌표 ("근거"를 보여줌)
- **정비 절차**: 어떻게 검사하고, 무슨 공구 챙기고, 뭘 조심하는지 (FAA 핸드북 출처)

→ "이 부품 뭐가 문제고, 전에 어떻게 했고, 어떻게 검사하는지"를 한 화면에.

### 서비스 ② 오케스트레이션 — "작업 흐름을 통제하는 화면"

정비 작업을 **12단계**로 나눠서, 각 단계에서 누가(정비사/AI/로봇) 뭘 하는지 보여줍니다.
핵심은 **"게이트"** — 잘못된 순서로 가는 걸 막습니다.
- 예: 위험한 작업은 **정비사 승인 없이는 다음 단계로 못 넘어갑니다.**
- 예: **AI는 "결함 후보"까지만 표시**하고, "결함이다"라고 확정하는 건 정비사만 할 수 있습니다.

→ 안내하는 게 아니라 **차단**한다는 게 포인트. "잘못 갈 수 있는 길 자체를 없앴다."

### 서비스 ③ 이동형 검사 로봇 — "로봇이 사각지대를 찍는 화면"

사람 손이 안 닿는 사각지대(동체 외판 안쪽 등)를 로봇이 대신 촬영합니다.
- 카메라 화면 + AI가 결함 후보를 표시 (여기서도 판정은 정비사)
- 음성으로 "여기 찍어줘" 하면 로봇이 이동·촬영
- 촬영 결과가 자동으로 작업 기록(Work Card)에 연결

로봇은 실제 제품(**뉴로메카 Indy7 팔 + Moby 이동대차**)을 기준으로 만들었습니다.

---

## 6. ④ 인터넷에 올리기 — "누구나 쓰게" (클라우드 배포)

### 왜 이게 필요했나

처음엔 서비스가 **내 컴퓨터에서만** 돌아갔습니다. 팀원한테 보여줄 수가 없었죠.
그래서 **인터넷(클라우드)에 올려서** 누구나 링크로 열 수 있게 했습니다.

### 어떻게 올렸나 (두 조각을 클라우드로)

우리 서비스는 두 부분으로 되어 있습니다:
1. **데이터(지식그래프)** — Neo4j
2. **화면과 서버** — 위 3개 화면

이 둘을 각각 무료 클라우드 서비스에 올렸습니다:

```
사용자 브라우저  →  Render(화면·서버)  →  Neo4j Aura(지식그래프)
                     둘 다 인터넷에 있음 → 내 컴퓨터 꺼도 됨
```

| 부분 | 올린 곳 | 무료? |
| --- | --- | --- |
| 지식그래프(데이터) | **Neo4j Aura** (클라우드 DB) | 무료 |
| 화면·서버 | **Render** (클라우드 호스팅) | 무료 |
| 코드 보관 | **GitHub** (코드 저장소) | 무료 |

### 결과

**https://mro-copilot.onrender.com** — 이 링크 하나면 누구나, 어디서나 서비스를 볼 수 있습니다.
내 컴퓨터를 켤 필요도 없습니다. 팀원에게 링크만 보내면 됩니다.

> ⚠️ 참고: 무료 서버라 15분간 아무도 안 쓰면 잠들었다가, 다시 열면 **첫 화면이 최대 50초** 걸립니다.
> 흰 화면이어도 기다리면 떠요. 발표 직전엔 미리 한 번 열어 깨워두면 됩니다.

### 앞으로 수정하면

코드를 고치고 **GitHub에 올리면(push)**, Render가 알아서 **자동으로 다시 배포**합니다.
링크는 그대로 유지되고, 몇 분 뒤 바뀐 내용이 반영됩니다.

## 7. 전체 여정 한눈에

```
[정비 지식이 흩어져 있다]
        ↓  ① 온톨로지 — 지식을 "관계"로 정리 (무엇을 연결?)
[FAA 공개 데이터로 연결 구조 설계]
        ↓  ② Neo4j — 컴퓨터가 읽는 지식그래프로 적재 (노드 1,300+ / 관계 2,500+)
[동그라미·선으로 저장된 지식]
        ↓  ③ 화면 3개 — 정비사가 쓰는 서비스로 (검색 / 오케스트레이션 / 로봇)
[사람이 보고 쓰는 화면]
        ↓  ④ 클라우드 배포 — 누구나 링크로 (Aura + Render)
[https://mro-copilot.onrender.com]
```

## 8. 핵심 3가지 (기억할 것)

1. **지어낸 데이터가 아니다** — FAA 공개 표준(JASC 547코드)과 실제 정비 보고 31,582건에서 나왔다.
   심사에서 "임의로 만든 거 아니냐"에 "실데이터·표준입니다"로 답할 수 있다.

2. **AI는 판정하지 않는다** — 구조 자체가 그렇게 되어 있다. AI는 "후보"까지만, 확정은 정비사만.
   "그렇게 하겠다는 약속"이 아니라 "그렇게밖에 안 되는 설계".

3. **작업 결과가 지식이 된다** — 정비사가 승인한 작업이 다음 검색에 다시 뜬다.
   작업할수록 대한항공만의 지식이 쌓이는 구조.

## 9. 폴더 어디에 뭐가 있나 (개발자용)

```
서비스/ (이 저장소)
├── server.js              화면과 지식그래프를 잇는 서버
├── index.html             서비스 ① 정비사 단말
├── orchestration.html     서비스 ② 오케스트레이션
├── robot.html             서비스 ③ 로봇 검사
├── docs/
│   ├── 서비스_제작여정.md   ← 이 문서
│   ├── 데이터정의서_v3.5.md  데이터 설계 상세
│   └── (프로토타입 화면들)
└── data/                  원천 데이터 (JASC·SDR 등)
```

더 깊은 기술 내용(온톨로지 7단계 설계·결정 기록·Neo4j 적재 스크립트)은
프로젝트 폴더의 `온톨로지/` 안에 단계별로 정리되어 있습니다.
